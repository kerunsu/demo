# 阶段4：分析框架实施规划

## 一、目标概述

### 核心目标
搭建一个**可扩展的分析框架**，确保后续分析模型、分析方法的接入足够顺利。

### 当前阶段任务
- 使用 Mock 分析器（返回假数据）验证整个流程的闭环
- 建立清晰的接口规范，方便后续真实模型接入
- 实现完整的数据流：录制数据 → 分析处理 → 结果存储 → 实时反馈

### 分析内容规划

| 类别 | 分析项 | 优先级 | 说明 |
|------|--------|--------|------|
| 视觉 | 身体姿态 (Pose) | 高 | MediaPipe/OpenPose 等 |
| 视觉 | 表情分析 (Expression) | 高 | 情绪识别 |
| 视觉 | 头部姿态 (HeadPose) | 高 | 头部朝向、注意力 |
| 视觉 | 眼动追踪 (EyeGaze) | 中 | 视线方向、注视点 |
| 视觉 | 物体检测 (Object) | 低 | 检测手持物体等 |
| 音频 | 语音特征 (Speech) | 高 | 说话时长、字数统计 |
| 音频 | 语音识别 (ASR) | 中 | 语音转文字 |
| 音频 | 情感分析 (Emotion) | 中 | 语音情感 |

### 核心接口设计

#### 1. 分析器基类接口

```python
class BaseAnalyzer(ABC):
    """所有分析器的基类"""
    
    @abstractmethod
    def analyze(self, data: Any) -> AnalysisResult:
        """执行分析，返回分析结果"""
        pass
    
    @abstractmethod
    def get_analyzer_type(self) -> str:
        """返回分析器类型标识"""
        pass
    
    @property
    @abstractmethod
    def is_ready(self) -> bool:
        """检查分析器是否就绪"""
        pass
```

#### 2. 分析结果数据模型

```python
@dataclass
class AnalysisResult:
    """分析结果数据模型"""
    session_id: str           # 会话ID
    analyzer_type: str        # 分析器类型
    timestamp: float          # 时间戳
    data: Dict[str, Any]      # 分析数据
    confidence: float         # 置信度 (0-1)
    metadata: Dict[str, Any]  # 元数据
```

#### 3. 流水线接口

```python
class BasePipeline(ABC):
    """分析流水线基类"""
    
    @abstractmethod
    def add_analyzer(self, analyzer: BaseAnalyzer) -> None:
        """添加分析器到流水线"""
        pass
    
    @abstractmethod
    def process(self, data: Any, session_id: str) -> List[AnalysisResult]:
        """处理数据，返回所有分析器的结果"""
        pass
```

## 七、关键设计决策

### 1. Mock数据的真实性

**建议**：Mock数据应该尽可能模拟真实模型的输出结构

- 姿态数据：使用标准的17关键点格式（COCO格式）
- 表情数据：使用常见的情绪分类（7类基本情绪）
- 音频数据：使用合理的数值范围

### 2. 分析频率控制

**建议**：

- 视觉分析：每5帧分析一次（30fps → 6次/秒）
- 音频分析：每1秒累积分析一次

### 3. 结果存储格式

**建议**：使用JSON格式存储

```json
{
  "session_id": "xxx",
  "results": [
    {
      "analyzer_type": "pose",
      "timestamp": 1234567890.123,
      "data": {...},
      "confidence": 0.95
    }
  ],
  "summary": {
    "total_frames": 1000,
    "analysis_count": 200,
    "duration": 33.3
  }
}
```

### 4. 错误处理策略

**建议**：

- 分析失败不应影响录制
- 记录错误日志，但继续处理
- 提供降级策略（如跳过失败的分析器）

   - 分析器应支持异步处理
   - 避免阻塞主线程
   - 考虑使用线程池

2. **资源管理**
   - 分析器应有清理方法
   - 及时释放模型资源
   - 监控内存使用

3. **向后兼容**
   - 保持现有API不变
   - 分析功能作为可选模块
   - 可以通过配置开关

4. **日志记录**
   - 记录分析耗时
   - 记录分析成功/失败次数
   - 便于后续优化

### 设计原则

- **开闭原则**：对扩展开放，对修改关闭
- **依赖倒置**：依赖抽象（基类），不依赖具体实现
- **单一职责**：每个分析器只负责一种分析
- **接口隔离**：视觉和音频分析器有独立的接口
