# 三端协同稳定性根因与分阶段整改方案

## 1. 文档目的

本文档用于指导 E.I.Art 系统按优先级逐项恢复稳定性，覆盖：

- Server 拉取代码、准备环境和一键启动；
- 机器人儿童端解压后双击 `start`，启动 DollSer、Robot Runtime 和运维界面；
- 教师端选课、课前准备、开始上课和课堂控制；
- 机器人语音、动作、表情和儿童端下屏内容的同步执行；
- 三端版本、日志、故障定位、测试和发布机制。

本文档不是一次性重写计划。整改原则是：先恢复一条最小、稳定、可回滚的课堂主链，再逐项接回增强能力。

---

## 2. 核心目标与优先级

### 2.1 唯一核心目标

形成连贯、稳定、可诊断的三端协同：

```text
Server 可复现启动
  → Robot Runtime 真实就绪
  → 教师选课并开始上课
  → 真实录制首样本到达
  → 进入控制页
  → 多模态行为完整同步
  → 行为结束并无缝回待机
```

### 2.2 优先级定义

- **P0：阻断课堂**。闪退、白屏、不能开课、录制假成功、多模态主链失效。
- **P1：高概率不稳定**。版本漂移、并发竞态、不可回滚、日志无法定位。
- **P2：工程质量**。自动化测试、发布门禁、长期维护和性能优化。

### 2.3 必须遵守的业务原则

1. M2“真实录制与采集”是唯一开课硬门禁。
2. 注意力、情绪、ASR、模型、资源预取和附加设备不得阻塞开课。
3. 在线心跳不等于设备可录制，也不等于三端版本兼容。
4. 课堂启动期间禁止安装依赖、下载模型或构建前端。
5. 每个行为的声音、动作、表情和儿童动画必须使用同一组关联标识。
6. 每项整改必须可独立验证、可独立回滚，不得一次修改全部链路。

## 3. 当前已确认的问题

## 3.1 P0：教师端课前准备存在直接闪退点

### 现象

- 课前准备失败或降级时页面闪退、白屏或卡死。
- 进入控制页后，发出教师控制命令可能出现异常。

### 已确认原因

1. `TrainingReadinessDialog.tsx` 的降级状态使用了 `AlertTriangle`，但没有导入该组件。
2. `ControlPage.tsx` 的 Socket 出站审计回调使用了当前作用域未定义的 `API_BASE`。
3. TypeScript 静态检查当前失败，发布流程没有阻止有前端错误的版本运行。

### 关键文件

- `teacher_frontend/components/TrainingReadinessDialog.tsx`
- `teacher_frontend/components/ControlPage.tsx`
- `teacher_frontend/package.json`
- `teacher_frontend/tsconfig.json`

### 整改任务 T01：消除教师端运行时错误

- [ ] 补全 `AlertTriangle` 导入。
- [ ] 将 `API_BASE` 提升为文件级唯一常量，禁止局部同名定义。
- [ ] 检查所有 `包名@版本号` 形式的无效前端导入。
- [ ] 补齐缺失的直接依赖和类型依赖。
- [ ] 为教师端顶层增加错误边界，避免单组件异常导致整页白屏。
- [ ] 在错误边界中显示错误编号和重试入口，不直接吞掉异常。

### 验证方法

```powershell
cd teacher_frontend
npm ci
.\node_modules\.bin\tsc.cmd --noEmit -p tsconfig.json
npm run build
```

人工验证：

1. 模拟 M1、M3、M4、M5、M6、M7、M8 分别降级。
2. 确认弹窗正常显示黄色降级状态，不白屏。
3. 进入控制页，触发任意教师 Socket 命令。
4. 确认浏览器控制台没有 `ReferenceError`。

### 完成标准

- TypeScript 检查和生产构建通过。
- 所有降级状态均可正常渲染。
- 教师端异常能够显示明确错误，不会整页闪退。

## 3.2 P0：课前准备的实际顺序与需求相反

### 现象

- 硬件连接正常，但课前准备长时间停留在检测中。
- 设备探测成功后，正式录制仍可能失败。
- 页面统一等待约 45 秒，教师不知道卡在哪一步。

### 已确认原因

当前严格预检大致顺序为：

```text
readiness_start
  → _run_server_checks
      → Runtime /devices/check
      → 打开摄像头和麦克风取样
  → readiness_prepare
  → _start_strict_capture
```

这意味着设备诊断在正式录制前同步执行。M8 虽然名义上不是硬门禁，但它在 M2 启动之前运行，仍可实际阻塞开课。

独立探测还会造成设备“打开—关闭—重新打开”，引入驱动释放延迟和设备占用竞态。

### 关键文件

- `app/services/readiness_service.py`
- `app/acquisition/device_preflight_runtime.py`
- `app/sockets/handlers.py`
- `app/sockets/events.py`
- `robot_runtime/agent.py`
- `static/js/child.js`

### 整改任务 T02：建立唯一录制状态机

建议状态：

```text
reserved
  → capture_start_requested
  → capture_process_started
  → first_sample_received
  → ready
```

失败统一进入：

```text
failed(errorCode, detail, retryable)
```

实施项：

- [ ] 先启动正式采集，再启动后台诊断。
- [ ] 不再通过独立设备探测结果放行 M2。
- [ ] 正式录制打开设备时产生的首帧/首音频块同时作为设备检查证据。
- [ ] M2 成功必须关联相同的 `trainingSessionId`、`mediaSessionId` 和 `generation`。
- [ ] 服务端记录首个有效媒体序号、接收时间和数据类型。
- [ ] M1、M3–M8 全部放入后台诊断线程或任务队列。
- [ ] M2 首样本到达后立即发送 `readiness_complete`。
- [ ] 开课主超时缩短至可配置的 8–12 秒。
- [ ] 所有后台诊断都设置有限超时，超时后变为 `degraded`。
- [ ] 重试时复用同一训练会话，增加 generation，拒绝旧 generation 回报。

### 验证方法

至少验证以下组合：

| 场景 | 预期结果 |
|---|---|
| 摄像头和麦克风正常 | 收到首样本后立即进入控制页 |
| 注意力模型失败 | 允许开课，M3 显示降级 |
| 情绪模型失败 | 允许开课，M4 显示降级 |
| 音频资源缺失 | 允许开课，M7 显示降级 |
| Runtime 心跳在线但摄像头打不开 | M2 失败，不能开课 |
| 只收到客户端 `recording=true` | 不能放行 |
| 收到旧 generation 首样本 | 忽略，不改变新状态 |
| 重复点击开始上课 | 不创建第二场录制 |

### 完成标准

- M2 是唯一硬门禁。
- 正式采集不再等待分析和资源检查。
- 设备不会因“预检一次、正式录制再开一次”被重复占用。
- 失败能够显示具体设备、阶段和错误码。

## 3.4 P0：环境检查会产生假成功

### 现象

- `bootstrap --check-only` 显示 Python 依赖基本正常。
- 实际运行时 MediaPipe API 不兼容、Torchaudio 缺失。
- FunASR 模型准备反复运行并出现 1800 秒超时。
- `node_modules` 目录存在，但前端类型检查仍失败。

### 已确认原因

1. Python 环境只检查 `flask` 和 `dotenv` 能否导入。
2. 没有验证依赖版本是否符合项目约束。
3. 有系统 Python 可用时不会强制创建项目虚拟环境。
4. Node 环境只检查 `node_modules` 是否非空。
5. 模型安装与业务服务启动混在一起。
6. 多个 Server 进程可重复拉起模型准备进程。

### 关键文件

- `scripts/bootstrap.py`
- `requirements.txt`
- `requirements-optional-analyzers.txt`
- `tools/voice-service/requirements.txt`
- `app/utils/voice_service_launcher.py`
- `.env.example`

### 整改任务 T04：建立可复现的 Server 环境

- [ ] 选定并固定生产 Python 版本，建议 3.10 或 3.11，验证完成前不使用任意系统 Python。
- [ ] 强制使用项目专用 `.venv`。
- [ ] 将宽泛的 `>=` 依赖改为经过验证的锁定版本。
- [ ] 明确 MediaPipe、NumPy、Torch、Torchaudio 的兼容矩阵。
- [ ] `bootstrap --check-only` 校验全部关键 import 和版本。
- [ ] Python 检查中实际初始化必要分析器，而非只 import Flask。
- [ ] Node 检查执行 `npm ci`、TypeScript 检查和生产构建。
- [ ] `.env` 缺失时明确失败，并显示需要填写的关键字段。
- [ ] Voice Service 模型准备改为单独的安装步骤。
- [ ] 正式 Server 启动期间禁止 pip install 和模型下载。
- [ ] 模型目录写入带版本和校验和的 manifest。

### 建议拆分命令

```text
setup.ps1      安装依赖、下载或导入模型、构建前端
check.ps1      只读检查环境、资源、端口、版本和模型
start.ps1      只启动已经准备好的服务
```

### 完成标准

- 在一台干净机器上能够按固定步骤复现环境。
- 缺少 Torchaudio 或 MediaPipe 不兼容时，检查阶段直接失败。
- 重启 Server 不会再次下载模型。
- 同一台机器只能有一个正式 Server 和一个 Voice Service 实例。

## 3.6 P0：多模态同步仍然依赖 Server 估时

### 当前问题

现有实现已经具备行为锁、`behaviorId`、语音等待和儿童动画等待，但动作仍在 Server 到达锚点后才通过 HTTP 下发给 Runtime。因此动作实际开始时间必然比表情和语音晚一个网络请求及 Runtime 处理时间。

另外：

- Runtime 动作使用独立生成的 requestId；
- 动作没有真实 started/ended 回执；
- 表情完成关联字段不足；
- 部分完成状态依赖计划时长而非实际执行结果；
- 全局单行为锁会让一个长超时阻塞后续所有行为。

### 关键文件

- `app/robot/robot_service.py`
- `app/sockets/events.py`
- `app/sockets/robot_events.py`
- `robot_runtime/agent.py`
- `robot_runtime/osc_bridge.py`
- `static/robot/js/emotion_display.js`
- `static/js/child.js`

### 整改任务 T06：统一行为信封

所有模态统一携带：

```json
{
  "protocolVersion": "1",
  "sessionId": "...",
  "requestId": "...",
  "behaviorId": "...",
  "startAtServerMs": 0,
  "modality": "speech|motion|expression|childAnimation"
}
```

- [ ] 禁止 Runtime 为动作另行生成不相关 requestId。
- [ ] 语音、动作、表情、儿童动画完成回执全部校验三个 ID。
- [ ] 完成回执增加 modality 和 terminal status。
- [ ] 旧回调、重复回调和其他 session 回调必须忽略。

### 整改任务 T07：实现 Prepare/Commit 同步协议

```text
Server 创建行为
  → 各模态 prepare
  → 各端返回 ready
  → Server 选择未来 300–500 ms 的共同锚点
  → 一次 commit
  → 各端按本地校准时钟等待锚点
  → 各端返回 started
  → 各端返回 ended/failed/timeout
  → 最长必需模态结束后释放行为
```

- [ ] 动作数据必须在锚点之前发到 Runtime。
- [ ] Runtime 本地等待锚点后启动动作。
- [ ] 表情页预解码，在锚点显示。
- [ ] 儿童端动画预加载，在锚点显示。
- [ ] 语音在锚点开始播放，不重复叠加服务端耗时。
- [ ] 必需语音 prepare 失败时，整组行为在视觉输出前取消。

### 整改任务 T08：建立真实最长模态屏障

- [ ] 每个行为冻结 required modalities 集合。
- [ ] 每个模态只有一个幂等 terminal 状态。
- [ ] 必需模态全部 terminal 后才能释放行为锁。
- [ ] 模态超时记录为 timeout/degraded，不得永久占锁。
- [ ] 动作优先使用 Runtime 真实 ended 回执；无回执时才使用估算并标记 unverified。
- [ ] 行为结束后立即恢复待机，不增加固定 500 ms 延迟。
- [ ] 新行为开始时取消尚未执行的待机回归。

### 完成标准

- 提问、提示、表扬、社交行为均使用同一事务。
- 四模态启动偏差不超过约定阈值，建议初始目标 150 ms。
- 任意短模态完成不会提前释放行为。
- 旧回调不能结束新行为。
- 行为完成后无黑屏、闪烁或明显待机空档。

## 3.7 P1：核心文件和全局状态过度集中

### 现状

- `app/sockets/events.py` 同时承担连接、教师租约、课程、录制、行为、对话、审计等职责。
- `app/robot/robot_service.py` 同时承担配置、调度、锁、动作、表情、Runtime HTTP 和完成屏障。
- readiness、Runtime 注册和部分行为状态保存在进程内存。
- 多进程或多个 Server 实例下可能出现状态不一致。

### 整改任务 T09：按用例拆分协调器

建议边界：

```text
Socket handler
  → TrainingStartCoordinator
  → CaptureCoordinator
  → BehaviorCoordinator
  → RuntimeClient
  → Timeline/Audit writer
```

- [ ] Socket handler 只负责鉴权、校验、DTO 转换和调用用例。
- [ ] 录制状态只能由 CaptureCoordinator 修改。
- [ ] 行为状态只能由 BehaviorCoordinator 修改。
- [ ] Runtime HTTP 统一封装到 RuntimeClient。
- [ ] 每个等待有唯一 owner、完成条件和超时。
- [ ] 禁止模块间直接修改对方的内部字典和事件对象。
- [ ] 单机部署先强制单正式进程；未来多进程再引入 Redis 等共享协调后端。

### 完成标准

- 单个入口文件不再包含完整业务状态机。
- 可以独立测试开课协调器和行为协调器。
- 同一个状态不会同时存在多份“真相”。

## 3.8 P1：源码、运行数据和构建产物混在一起

### 当前风险

当前工作区包含大量未提交源码修改，同时数据库、日志、pycache、Vite 缓存、dist 和发布包也处于变化状态。这导致：

- 无法确定课堂运行的准确源码；
- 无法安全回滚；
- 打包可能混入旧构建产物；
- 测试可能污染发布差异；
- 每次修补都难以定位真正回归点。

### 整改任务 T10：恢复版本和发布纪律

- [ ] 保存当前现场为独立诊断分支或归档包。
- [ ] 数据库、日志、录制、pycache、Vite cache 和临时目录退出源码跟踪。
- [ ] 课程资源、配置和运行数据明确区分。
- [ ] 发布只能从干净工作区生成。
- [ ] 发布清单写入源码 commit 和工作区是否干净。
- [ ] 建立 `stable-baseline`、`current-recovery` 和 `next` 三条线。
- [ ] 旧稳定分支只用于黄金流程和回归对照，不整体覆盖当前代码。
- [ ] 每完成一个任务独立提交，提交信息标注对应任务号。

### 完成标准

## 7. 当前检查结论摘要

1. 当前硬件首帧和首音频块检查能够通过，硬件连接不是首要根因。
2. 教师端存在确定的未定义组件和变量，可直接造成白屏或交互异常。

4. 现场 Runtime 与 Server 发布版本不一致，但系统没有阻止协议漂移。
5. Server 环境检查过于宽松，无法发现实际分析依赖不兼容。
6. 多模态已有部分原子化机制，但动作仍未在 Runtime 端按共同锚点启动。
7. 后端测试通过不能覆盖当前前端错误和真实三端竞态。
8. 当前工作区修改和运行产物混杂，必须先建立干净、可回滚的整改基线。

整改时不要先继续微调固定延迟。当前首要问题是环境、版本、状态机和协议生命周期，而不是某个动作或表情多延迟几十毫秒。
