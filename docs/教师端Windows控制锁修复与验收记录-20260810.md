# 教师端 Windows 控制锁修复与验收记录（2026-08-10）

## 1. 现场现象

教师端能够正常打开、登录和查看学生，但点击“开始评估”或“开始训练”时弹出：

```text
[Errno 22] Invalid argument: '.runtime\\coordination\\teacher_leases.lock'
```

页面本身不是根因。错误发生在服务端为训练会话申请教师控制权时，底层 Windows
文件锁异常被直接放入 `prepare_training_ack`，教师端收到失败确认后显示弹窗。

## 2. 根因

旧的进程锁实现存在三个缺口：

1. 打开锁文件发生的 `OSError` 不在异常保护范围内。
2. `TeacherControlRegistry` 忽略 `acquire()` 的失败返回值，可能在没有取得进程锁时
   继续加载和保存租约。
3. 解锁或关闭阶段的 Windows 异常可能覆盖已经成功的业务操作，并穿透到教师端。

现场还发现两个 `app.py` 进程同时存活。虽然只有一个监听 8080，但旧进程增加了
状态归属和排障歧义。两个进程均经命令行和 PID 核验后结束，随后只启动一个加载
修复代码的服务端实例。

## 3. 已实施修复

- 进程锁路径在对象创建时解析成绝对路径，不受运行期间工作目录变化影响。
- 阻塞获取遇到瞬时打开/加锁错误时执行三次有限重试，退避为 50 ms、100 ms。
- 解锁阶段的 `seek`、Windows `LK_UNLCK` 或关闭错误被隔离；关闭文件描述符仍会
  释放操作系统持有的锁，不再把成功业务改写成失败。
- 教师租约只有在确认取得进程锁后才能加载和保存。最终仍无法获取时返回稳定错误码
  `teacher_control_temporarily_unavailable`，不再暴露底层文件路径和 errno。
- 保留教师端已有的请求去重和 `finally` 恢复：失败、超时或重复点击后，“正在准备”
  状态都会退出，按钮可以继续使用。

## 4. 自动化验证

新增回归覆盖：

- 首次打开锁文件模拟 `[Errno 22]`，后续重试成功。
- 解锁阶段模拟 `Errno 22`，业务调用不被异常覆盖。
- 未取得进程锁时教师租约不得写盘。
- 两个本机注册表实例仍遵守同一 OS 锁和控制权规则。

执行结果：

```text
python -m pytest -q
355 passed, 110 warnings
```

warnings 为既有的 `datetime.utcnow()`、SQLAlchemy legacy API 等弃用提示，不是本次
功能失败。

## 5. 内置浏览器真实点击

测试入口：`http://192.168.1.110:8080/teacher/`，真实教师会话 `djt`。

1. 学生 `djt` 档案页正常显示。
2. 普通点击一次“开始训练”：约 1.5 秒进入课程选择，没有锁弹窗。
3. 返回学生页：服务端成功执行 `cancel_prepare_training`。
4. 双击“开始训练”模拟误操作：仍只进入一个课程选择流程，没有弹窗或页面卡死。
5. 再次返回：第二个准备流程成功取消。
6. 浏览器页面 console 的 error/warn 为空。
7. 最终 `.runtime/coordination/teacher_leases.json` 中 `leases=[]`，Server 活动
   sessions 为 0，没有残留控制权或录制会话。

对应服务端日志：`.runtime/logs/backend-20260809-235353.stderr.log`。其中两次
`prepare_training` 均为 `success=True`，两次 `cancel_prepare_training` 均为
`success=True`，没有 `Errno 22` 或 `teacher_control_temporarily_unavailable`。
