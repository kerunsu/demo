# 交互延迟诊断与语音策略检查

本文描述教师端一次交互指令到机器人多模态反馈的实际链路、测量口径、自动归因和当前语音策略风险。诊断是只读的：它增加时间点和报告，不改变动作、表情、儿童下屏或语音的播放顺序与状态机语义。

## 1. 使用入口

Server 控制端进入 `配置中心 -> 交互延迟诊断`，选择一场训练会话后可查看：

- 教师浏览器到 Server 的 Socket RTT；
- Server 收到指令到行为排队、下发和 ACK 的内部耗时；
- 为动作、表情、下屏和语音同时起播而有意保留的同步时间；
- 四个模态从 Server 收到教师指令到终端真实启动回执的耗时；
- 最近 50 次交互的逐次拆解、最慢交互时间轨和主要来源判断；
- 下屏预检、加载/解码、绘制等待、淡入各阶段耗时；
- 自然对话从停声截句、编码、FunASR、决策到浏览器实际开口的分段；
- 儿童语音交互的五种状态机模拟及风险；
- Markdown 诊断文档与完整 CSV 原始日志。

页面可每 5 秒刷新。列表按媒体录制会话选择，而不是只按可能复用的
`trainingSessionId` 选择。日志沿用训练会话目录中的
`full_interaction_timeline.jsonl`，不新增数据库，也不会修改历史录音。
修复前若多个重试误写进首个目录，读取层只会恢复 `sessionId` 与当前
录制轮次严格相等的行，并在页面黄色提示恢复数量；无法证明归属的旧行
不会被猜测或并入报告。

## 2. 一次按钮触发的真实链路

```text
教师点击
  -> teacher Socket emit（clientCommandAtMs）
  -> Server 收到 play_resource
  -> 校验控制权 / 幂等 / 行为忙碌
  -> 行为状态机 reserve + prepare
  -> 计算统一 startAt
  -> 下发到儿童端、机器人显示端、Robot Runtime、语音端
  -> 各端素材准备 ready
  -> 到达 startAt 后实际 started
  -> Server 收到 ready/started 回执
```

当前默认存在约 700ms 的统一起播预留，最低安全余量约 200ms。它用于让不同电脑、浏览器媒体和 Robot Runtime 在同一目标时刻起播，是系统内部的有意等待，不应误判为网络卡顿。儿童下屏媒体切换会先做同源资源预检，再进行真实 iframe/图片/视频加载和解码，等待两个绘制帧，最后执行约 320ms 淡入；交互页面因此可能发生两次请求和完整页面初始化。文件语音预加载有 5 秒失败上限，浏览器 TTS 有独立的看门狗与重试。这些上限不等于每次实际延迟，实际值以会话报告为准。

## 3. 时间点和计算口径

| 时间点 | 事件 | 时钟与含义 |
|---|---|---|
| 教师发出 | `teacher_socket_emit.play_resource` | 教师浏览器在 emit 前记录 |
| Server 收到 | `latency.play_resource_received` | Server 时钟，网络之后的第一站 |
| 行为排队 | `robot_behavior_queued` | Server 时钟，包含计划 `startAtEpochMs` |
| 多模态下发 | `latency.multimodal_dispatched` | Server 时钟，所有准备完成并开始下发 |
| Server ACK | `play_resource_ack` | Server 时钟，教师端收到前的响应生成点 |
| 终端就绪 | `latency.modality_ready_callback` | Server 收到终端 ready 回执的时刻 |
| 终端开始 | `latency.modality_started_callback` | Server 收到终端 started 回执的时刻 |
| 对话音频收到 | `dialogue.audio_received` | Server 收到儿童端编码音频的时刻 |
| 语音识别结束 | `dialogue.stt_completed` | 同一 Server 时钟上的 FunASR 实际调用耗时 |
| 对话决策结束 | `dialogue_reply_generated` / keyword / wake | 课程关键词、唤醒或 LLM 决策结束 |
| 浏览器开口 | `dialogue.client_tts_started` | Server 收到儿童浏览器实际 TTS 开始回执 |

报告中的主要指标：

- `教师网络 RTT`：教师端定时 Socket ping/ACK 的往返耗时。单程网络只能近似为 `RTT / 2`。
- `Server 排队`：`行为排队 - Server 收到`。
- `Server 下发`：`多模态下发 - Server 收到`。
- `同步预留`：`计划 startAt - 行为排队`。
- `模态端到端`：`Server 收到终端 started 回执 - Server 收到教师指令`。
- `终端接收到开始`：同一终端的 `actualAtClientMs - commandReceivedAtClientMs`，不受两台电脑墙上时钟不同步影响。
- `计划后尾延迟`：终端 started 回执到达 Server 的时刻晚于计划 startAt 的部分。它同时包含终端启动耗时和回传网络，不能仅凭这一项断言硬件慢。
- `自然对话端到端`：`dialogue.client_tts_started - dialogue.audio_received`；截句前的静音等待由客户端单独上报，避免误归因给 Server。

跨电脑绝不直接相减两个墙上时钟。Server 内部阶段使用同一 Server 时钟；终端内部阶段只使用同一终端的时间差；网络使用 RTT 估计。

## 4. 自动归因规则

页面比较四类贡献：

1. `network`：教师 RTT 的单程估计；
2. `server`：Server 校验、解析、排队；
3. `sync`：状态机有意保留的统一起播窗口；
4. `endpoint`：计划起播之后仍未观察到开始的尾延迟。

当前告警线是诊断提示，不是硬性 SLA：

- 网络 RTT P95 达到 200ms：提示教师端网络往返偏高；
- Server 下发 P95 达到 300ms：提示 Server 内部处理偏慢；
- 同步预留 P50 达到 500ms：明确标记为有意同步，而不是故障。

第一次使用应至少采集 20 次同一类按钮操作，分别在本机局域网稳定、网络拥塞和不同素材长度下比较 P50/P95。单个样本只能定位一次异常，不能作为长期调参依据。

## 5. 四种反馈应如何判读

- 表情：关注显示端 `ready -> started`。若 Server 下发快而表情晚，检查 MP4 解码、显示页面是否后台降频及显示端网络。
- 动作：关注 Robot Runtime prepare/started。旧 Runtime 只有 `dispatched` 时，页面会明确标为“下发代理，非实际起动”，不能把它当成机械臂首动时间。
- 下屏：`resource_ready` 表示新资源已解码并完成可见切换。互动页不再先做一次重复 HTTP 预检；可见转场为 160ms。若仍仅下屏晚，优先检查文件大小、浏览器解码和 iframe 自身初始化。
- 语音：`audio_status=playing/started` 是实际开始。若文件语音慢而 TTS 正常，检查文件获取和解码；若 TTS 慢，拆查生成服务和浏览器 TTS 启动。

“未配置/未上报”不等于零延迟，可能是本次行为没有该模态、对应终端离线，或终端仍是旧版本。报告不会用零填补缺失样本。

## 6. 儿童真实语音交互模拟

本次按现有状态机做了确定性路径检查，没有伪造真实麦克风或硬件结果：

| 场景 | 当前表现 | 结论 |
|---|---|---|
| 说“麦麦”后立即回答 | 唤醒回复结束后保留 700ms pre-roll，180ms 冷却后仍可命中课程关键词 | 已覆盖 |
| 机器人尚在说话时抢答 | 为避免扬声器回采，TTS 期间暂停 ASR 并清空缓冲 | 高风险：现场会感觉“没听见” |
| 嘈杂教室中轻声回答 | 固定 VAD 起声/静音门限可能漏掉轻声或延后截句 | 中风险：需真实教室标定 |
| 先答错再答对 | 未命中不会消费当前题，后续正确答案仍可触发一次表扬 | 已覆盖 |
| 唤醒后切换下一题 | 题目/课点指纹变化会重置唤醒状态 | 有意隔离上下文 |

课程答案判断优先于普通 LLM 对话；关键词命中后直接进入既有表扬和下一题链路，不创建第二套流程。当前最需要现场验证的是“抢答”与回声保护的冲突，以及不同儿童音量/距离下固定 VAD 的漏检率。此次只定位并展示风险，没有改变 ASR 门控和 VAD 参数。

自然对话的固定等待首先来自儿童端 VAD：确认起声约 180ms，停声后约 900ms 才截句，并保留约 700ms pre-roll；随后才是音频编码与上传、WAV 转换、本机 FunASR、必要时的 voice-service 回退、课程关键词/唤醒/LLM 决策、浏览器 TTS 排队和实际开口。Server 页面会把本机识别尝试和远端回退分别显示；稳定局域网中网络通常不是最大项，但必须用当前会话的 RTT 和每轮分段确认，不能用主观体感代替数据。

## 7. 建议的现场采样步骤

1. 重启 Server，并刷新教师端、儿童端、机器人显示端和 Robot Runtime，使新增时间字段全部生效。
2. 创建一次测试训练，每种提问、提示、表扬各触发至少 20 次。
3. 分别测试仅表情、仅动作、仅语音、含下屏切换和完整多模态组合。
4. 同时做正常回答、唤醒后快速回答、机器人说话时抢答、轻声回答、先错后对。
5. 在诊断页看逐次拆解，再下载 Markdown 和 CSV 留档。
6. 只有当同一来源在 P95 上持续占优时才调参数；每次只改一类参数并重复同一组样本。

真实摄像头、麦克风、扬声器、机械臂和跨电脑网络仍属于人工门禁。软件模拟和单元测试只能证明关联、计算与页面展示正确，不能替代现场时延测量。
